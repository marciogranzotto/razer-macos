## What We Built

### Drag-to-Swap + Undo/Redo (shipped)

- Spec: `docs/superpowers/specs/2026-04-22-button-mapping-drag-undo-design.md`
- Plan: `docs/superpowers/plans/2026-04-22-button-mapping-drag-undo.md`
- Single-file change in `src/renderer/sections/sectionsettingbuttonmapping.jsx` + one CSS rule in `src/renderer/index.css`

Design highlights:

- **Central dispatcher** `dispatchMappingChange(changes, { fromHistory })` funnels every mapping write (editor edit, restore-to-default, drag-swap). Captures before/after snapshots, fires IPCs, does an optimistic local update, and pushes a stack entry in a single functional `setState`.
- **Stack entries**: `{ type: 'single', layer, buttonId, before, after }` or `{ type: 'group', entries: [singles...] }`. Drag-swap produces a group → one undo reverts both sides atomically.
- **Cap 50 entries**; redo cleared on any new change.
- **Stack clears** on: `profile-switched`, `slot-saved`, `slot-cleared` (if cleared slot was active), `handlePanelTypeResponse` (if panel changed), `handlePanelChanged`. Layer toggle does NOT clear.
- **Keyboard**: `cmd+z` / `cmd+shift+z`, registered on `document`. Guards against hijacking during key recording, in inputs, or when component has no panel/feature.
- **Cross-layer undo**: auto-switches layer (with `mappings: []` reset and `requestMappings()` after `commit()`, not before — matters because set-button-mapping must reach the hardware before the get-button-mappings re-fetch).
- **Drag visuals**: source cell opacity 0.4, target cell gets green outline `#47e10c`. `e.currentTarget.contains(e.relatedTarget)` guard in `handleDragLeave` avoids flicker from child-div boundaries.

### Bug 1: DPI Slider UI Refresh (shipped)

**Symptom:** Switching profiles didn't update the DPI slider display.

**Root cause:** `deviceSelected` in the renderer is a snapshot from `showView`. `this.dpi` on the main-process device instance updates, but never propagates to the renderer. Additionally, `MouseSensitivity` uses `useState(dpi)` — reads the prop on mount only, ignores subsequent changes.

**Fix (commit `a72aff9`):**
1. Main process includes `dpi: currentDevice.dpi` in `profile-switched` and `slot-cleared` IPC replies; calls `refreshTray()` so tray menu reflects new active profile.
2. `SectionSettingSensitivity` holds `dpi` in local state, listens for both events, updates state on receipt, and sets local state optimistically on slider clicks.
3. `MouseSensitivity` syncs `currentDpi` to the `dpi` prop via `useEffect(() => setCurrentDpi(dpi), [dpi])`.

## What We Learned (Bug 2 diagnostic findings)

Added `[DPI-DIAG]` logging (commit `6d4e26c`) that reads back all five slot DPIs after every write and every profile switch. User ran the diagnostic. The output revealed:

### Finding 1: `mouseGetActiveProfile` returns `0`

```
setDPI(dpi=6194, profile=null) → p=0, activeProfile=0
```

The hardware reports profile `0` at startup, not 1–5. Either the Naga V2 Pro uses 0-indexed profiles internally, or the command `0x05:0x82` isn't the correct READ_ACTIVE_PROFILE for this model. All downstream code (mirror-to-slot-1 guard, etc.) assumes 1-indexed 1–5.

### Finding 2: Per-profile DPI read returns garbage

Read-back after any write is identical regardless of what we wrote:

```
slot1=1285, slot2=1029, slot3=1029, slot4=1029, slot5=773
```

Values `0x0505`, `0x0405`, `0x0305` look like DPI stage metadata — `current_stage | (max_stages << 8)` or similar — not stored DPI in raster units. My driver's `razer_mouse_attr_read_dpi_profile` (command `0x04:0x86`) probably isn't the right read for per-profile stored DPI.

### Finding 3: Per-profile DPI write only takes effect via VARSTORE

Only `mouseSetDpiProfile(..., 1, dpi_x, dpi_y)` (i.e. `arg[0]=1=VARSTORE`) actually changes the mouse's live DPI. Writes with `arg[0]=2,3,4,5` are silently no-op or interpreted differently (possibly as `NOSTORE` / invalid). That's why the mirror-to-slot-1 strategy "works" for live DPI — but the real per-slot storage never gets written, so switching back to an old profile gets Synapse's original value, not what the user set in our app.

### Finding 4: User's observed symptom is fully explained

- User on profile 2, sets DPI 6400: wrote to "slot 2" (no-op) and mirror slot 1 (VARSTORE, 6400) → mouse fast ✓
- Switch to profile 3: read "slot 3" → garbage/stale (1029), write 1029 to slot 1 → mouse slow ✓
- Switch back to profile 2: read "slot 2" → Synapse's original value (not user's 6400) → mouse still slow ✓
- Re-apply 6400: VARSTORE write → mouse fast again ✓

## Next Steps (Bug 2: DPI Per-Profile Persistence)

The proper fix abandons the "mirror to slot 1 via per-profile DPI commands" strategy for DPI, and uses the standard Razer pattern: `SET_PROFILE` to switch the hardware's active memory slot, then standard VARSTORE reads/writes that operate on whatever slot is active.

### Preflight investigation (required before protocol redesign)

1. **Verify `SET_PROFILE` command ID.** `razer_mouse_attr_write_active_profile` uses `0x05:0x03`. Does this actually move the hardware's active slot on a Naga V2 Pro? Test by sending `SET_PROFILE(2)` then reading back current DPI via standard VARSTORE read — does it match what's in slot 2?

2. **Verify `GET_ACTIVE_PROFILE` command ID.** Finding 1 showed it returns `0`. Check Linux `openrazer` for the Naga V2 Pro's actual command (may be `0x05:0x84` or similar). If it's really 0-indexed, that affects all downstream logic.

3. **Verify whether standard `0x04:0x05` VARSTORE writes persist to the currently-active slot.** Expected yes, but confirm with a SET_PROFILE → VARSTORE-write → SET_PROFILE(other) → SET_PROFILE(back) → VARSTORE-read roundtrip.

4. **Check whether `SET_PROFILE` triggers side effects** (profile indicator LED blink, lighting changes) and decide if that's acceptable.

5. **Investigate the actual per-profile DPI read protocol.** Capture a USB trace of Synapse on Windows switching profiles to see what reads it actually issues. Suspect there's a real per-profile DPI read we haven't found yet.

### Implementation path once protocol is confirmed

- Remove per-profile DPI driver functions (`razer_mouse_attr_read_dpi_profile`, `razer_mouse_attr_write_dpi_profile`) OR keep them but re-base on SET_PROFILE + VARSTORE.
- `switchProfile(N)`: send `SET_PROFILE(N)`, then standard VARSTORE DPI/button reads will reflect slot N.
- `setDPI(dpi)`: standard VARSTORE DPI write (no mirror). Operates on currently active slot.
- `saveToSlot(targetSlot)`: `SET_PROFILE(targetSlot)` → write current buttons/DPI via standard commands.
- Revisit button-mapping mirror logic — it may or may not be needed depending on whether the protocol's built-in profile byte actually works for buttons (needs confirmation, unlike DPI where we've proven it doesn't).
- Update `this.activeProfile` handling if hardware is 0-indexed.
- **Remove `[DPI-DIAG]` logging** (commit `6d4e26c`) once stable.

### UX considerations

- The DPI slider currently shows whatever the broken read returned after a switch. After the fix, it'll show the real per-slot DPI — no further renderer changes should be needed because the existing IPC plumbing from `a72aff9` already refreshes it.
- If `SET_PROFILE` has hardware side effects, consider whether to preserve them or suppress (probably preserve — Synapse does too).

### Out of scope (deferred, not failures)

- `handleMappingsResponse` double round-trip noted in the final review of the drag-undo feature (two in-flight `get-button-mappings` during drag-swap) — pre-existing, low-impact.
- Heterogeneous-layer group entries (latent, currently unreachable in practice).

## Lessons Learned

- **Don't trust USB capture packets as canonical command docs.** The plan noted `0x04:0x86` as "observed in USB capture" and even flagged a fallback to `0x04:0x85`. In practice neither was verified per-slot. Future protocol work should include read-back verification in the plan itself.
- **The `useState(propValue)` antipattern is subtle.** A functional React component that accepts a changeable prop and initializes state from it *silently ignores prop changes*. Always pair with `useEffect(..., [prop])` or just read directly from props. Cost us an hour of debugging "why doesn't the slider update" before I found this.
- **Subagent-driven-development worked well** for a small 3-task feature. Final-branch review caught a real cross-layer IPC ordering bug that neither the per-task reviews nor a manual smoke test would have found (window is narrow and asymptomatic unless latency is high). The ceremony is worth it.
