## Executive Summary

Finished the per-profile protocol rewrite that the 2026-04-22 session teed up. The fork predictions from that session's preflight were partially right and partially wrong; an empirical command-sweep discovered that the Naga V2 Pro has **two operating modes** (HW vs PC) and the real SET_ACTIVE_PROFILE in PC mode is `0x05:0x04`, not `0x05:0x03`. ## What We Learned (major corrections to the 2026-04-22 fork predictions)

### The Naga V2 Pro has two operating modes

- **HW (stand-alone) mode**: profile LED colored per slot, physical profile button cycles slots, software SET_ACTIVE_PROFILE is inert (ACKed but ignored).
- **PC mode**: white LED, physical button dead, software fully in control.
- **Mode switch trigger**: writing anything to profile 1 flips HW → PC mode. No known command returns to HW mode; user would power-cycle.

This explained the whole "software SET sometimes works, sometimes doesn't" mystery that blocked us repeatedly during verification.

### GET_ACTIVE_PROFILE is `0x05:0x84`, not `0x05:0x82`

The old driver used `0x05:0x82` which NAKs on every call. The preflight plan guessed `0x05:0x02` based on Synapse traffic — also NAKs. An empirical sweep of all `0x05:0xNN` commands found `0x05:0x84`: response `arg[0]` is the 1-based active profile slot.

### SET_ACTIVE_PROFILE is `0x05:0x04`, not `0x05:0x03`

Same empirical sweep showed `0x05:0x04(N)` actually moves the active slot in PC mode (verified by `0x05:0x84` tracking it). The old `0x05:0x03` (which Synapse also sends) does *something else* on this device — possibly a default-profile setter or HW-mode-only command. Kept in driver for completeness, unused by device layer.

### DPI is per-profile, but NOT via VARSTORE

- VARSTORE DPI (`0x04:0x05` / `0x04:0x85`) is a single global register. Writes affect live cursor speed but don't persist per-profile.
- Per-profile DPI lives in the **stage table** (`SET_DPI_STAGES` = `0x04:0x06`, `GET_DPI_STAGES` = `0x04:0x86`). Each profile has 5 DPI stages + an active_stage index. When SET_ACTIVE_PROFILE moves the slot, the hardware loads the new slot's active-stage DPI into the live register.
- Format: `arg[0]=profile (1–5)`, `arg[1]=active_stage (1-indexed — 0 rejected)`, `arg[2]=num_stages`, then `num_stages × 7-byte` entries. Device rejects (status 0x03) if all stages have identical DPI.

### Button mapping remained Fork B (correct per-slot addressing)

This was the one fork prediction that stayed correct. `0x02:0x0c` writes land on the specified slot regardless of active profile. Mirror-to-slot-1 removed.

### Driver changes (`librazermacos/src/lib/razermouse_driver.c`)

- **Added** `razer_mouse_attr_activate_profile` — `0x05:0x04` PC-mode SET_ACTIVE_PROFILE.

- **Deleted** `razer_mouse_attr_read_dpi_profile` / `razer_mouse_attr_write_dpi_profile` — architecturally wrong (they sent `0x04:0x05` with `arg[0]=slot`, but on this device `arg[0]` is a VARSTORE flag there, not a slot number).
- **Added then removed** `razer_mouse_attr_probe_raw` — temporary helper for the empirical sweep.

### N-API bindings (`src/driver/addon.cc`)

- `mouseActivateProfile`
- `mouseSetDpiStages` — takes `(id, profile, active_stage, stages_array)` where stages_array is `[{x, y}, ...]`.
- `mouseGetDpiForProfile` — returns `{x, y, ok}`.
- Deleted: `mouseGetDpiProfile`, `mouseSetDpiProfile`, `mouseProbeRaw` (temporary).

### Device layer (`src/main/device/razerdevicemouse.js`)

- `slotDpi` map added to the device instance, populated at init from `mouseGetDpiForProfile` for all 5 slots.
- `setDPI(dpi, profile)` writes a 5-stage table via `mouseSetDpiStages` (stages centered on the user's value: `[dpi/4, dpi/2, dpi, dpi*2, dpi*4]`, active_stage=3). Updates the slot-dpi cache.
- `switchProfile(slot)` calls `mouseActivateProfile(slot)`, updates `this.activeProfile`, reads `this.dpi` from the cache (falls back to `mouseGetDpi` VARSTORE read when cache is null).
- `saveToSlot(targetSlot)` snapshots current state (button mappings from currently-active slot + current DPI), activates the target slot, writes button mappings (Fork B, direct per-slot writes) and DPI stage table to the target. MACRO_CLEAR as housekeeping.
- `setButtonMapping` no longer mirrors to slot 1.
- `init()` trusts `getActiveProfile()` (now functional via the `0x05:0x84` fix), seeds `this.dpi` from the correct slot's cached value.
- All `[DPI-DIAG]` diagnostic logging removed.

## Lessons Learned

- **Preflight fork predictions were confident but wrong.** The 2026-04-22 session's predictions of "Fork A for DPI, Fork B for buttons, wrong command ID for GET" were each partially right but the architectural model (HW vs PC mode, stage-table DPI) was undiscovered. Lesson: when observations are consistent with multiple hypotheses, the hypothesis must say which next observation would falsify it. The preflight probes didn't distinguish between "DPI is global" and "DPI is per-profile but stored somewhere we haven't read."
- **Empirical brute-force works.** Sweeping all 256 commands in a class, after SET-ing different slots, cleanly identified GET_ACTIVE_PROFILE in ~3 minutes. Worth keeping as a reusable technique for future Razer devices.
- **`active_stage=0` is rejected by the firmware.** Looks innocent in `(profile, active_stage=0, num_stages=5, stages...)` format; returns status 0x03. Had to try `active_stage=2` to get the first successful SET_DPI_STAGES, which led to the 1-indexing finding.
- **Identical-all-stages also rejected.** Device requires at least two stages with distinct DPI values. Our `setDPI` guards against this with a `seen` set + bumps.
- **"Writing to profile 1 flips the mouse into PC mode"** was user-discovered via LED observation during a smoke test. Not from captures, not from probes — just the user pressing the profile button and noticing the LED behavior changed. Lesson: the physical device itself has visible state (LED color, button responsiveness) that's hard to infer from protocol-level probing alone. Ask the user what they're seeing.
- **VARSTORE DPI vs stage-table DPI are independent registers.** The slider-not-updating bug at the end wasn't a code bug; VARSTORE simply doesn't track the active profile's stage DPI. The fix (per-slot cache populated from `GET_DPI_STAGES` reads) is conceptually simple once you know about the two-register design, but debugging would have been much harder without the diagnostic logs.

## Known Unresolved

- **Software SET "stuck" state.** After some operations, `0x05:0x04(N)` ACKs but doesn't move the active slot. Running `discover-get-active-profile.js`'s full sweep restores it. Root cause not pinned down. Documented in the protocol doc. Hasn't surfaced in normal app use yet.
- **`0x05:0x03` semantics.** Synapse sends this command; openrazer calls it SET_ACTIVE_PROFILE. On our device in PC mode it does *not* move the active slot. Possibly a HW-mode-only setter or a different semantic. Left in the driver for completeness; device layer doesn't use it.
- **HW-mode return path.** We don't know how to take the mouse out of PC mode back to HW mode. Probably requires a power cycle. Not relevant for the app but documented in case a user wants the colored profile LED back.
